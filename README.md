# Biomedical Internship Tracker

US STEM summer internships at biomedical, medical-device and pharmaceutical
companies and NIH research programs, read straight from each company's job
board and refreshed every day.

Each listing links to the employer's own posting. Apply there; this repository
only collects links.

- **Who it's for:** students looking for engineering, software, data, science,
  quality and regulatory internships in medtech and pharma.
- **What's included:** internships and summer co-ops in the US for the season
  below. Full-time, non-STEM, off-season, PhD-only and SkillBridge roles are
  filtered out.
- **What's not:** this list is only as complete as each company's public job
  board. A missing company or role doesn't mean nothing is open. Check the
  company's careers page too.

Spotted a listing that's closed or wrong? [Report it](https://github.com/KTB99/biomed-internship-tracker/issues/new?template=report-listing.yml).
Know a company the tracker should follow?
[Suggest it](https://github.com/KTB99/biomed-internship-tracker/issues/new?template=suggest-company.yml).

Within each role section, postings whose title says they're for undergraduates
come first, then postings open to any level. Postings whose title says they're
for graduate students (graduate, master's, MBA or PhD) are listed last, under a
dashed **Graduate students** divider. A posting whose title doesn't say counts
as open to any level, so read the posting itself before ruling it out.

Listings that close move to [CLOSED.md](CLOSED.md). The raw data is in
[`data/listings.json`](data/listings.json).

## Add an internship

Some tracked companies post their internships only on Workday, which the tracker
can't read (Alcon, Globus Medical, Insulet, Medtronic, ResMed, Smith+Nephew and
Tandem). If you find an open posting at one of them, anyone with a GitHub
account can submit it with the
[**Add internship**](https://github.com/KTB99/biomed-internship-tracker/issues/new?template=add-internship.yml)
issue form.
It asks for the company, title, Apply URL, location, term and, optionally, the
date applications close.

A maintainer reviews each submission and opens the Apply link to check that the
posting is open. The command they run (below) also checks the link is on that
company's own careers or Workday site and screens the posting like any other.
An accepted posting is added in a pull request and listed once it merges. It
closes when a maintainer closes it, or the day after its closing date if you
gave one. If the tracker can read the company later, a posting it reads at the
same Apply URL replaces the submitted one.

Maintainers accept a submission with:

```bash
gh issue view <N> --json body -q .body | python -m tracker add --issue <N> -
```

It writes nothing and says why when it refuses one: the company accepts no
submissions, the Apply URL isn't https on one of the company's `submit_hosts`
in [`companies.toml`](companies.toml), a field is missing, the closing date is
invalid or past, screening rejects the posting, or the tracker already has it.
See [ADR 0002](docs/adr/0002-submitted-listings.md).

## How it works

A scheduled GitHub Action runs `python -m tracker refresh` once a day. For each
company in [`companies.toml`](companies.toml) it:

1. Reads the company's public job board: Greenhouse, Lever, SmartRecruiters,
   Eightfold, Phenom, Oracle Recruiting Cloud, Pinpoint, TalentBrew, SAP
   SuccessFactors (jobs2web), Paradox, Attrax, Kentico job search, the job
   lists of sites built by Happy Dance, or JobPosting markup on the careers
   page. Workday's jobs API rate-limits the tracker, so a
   company that posts only on Workday is read from its careers page
   ([ADR 0001](docs/adr/0001-no-workday-jobs-api.md)).
2. Screens every posting: it must be an internship or summer co-op, in the US,
   STEM, for the target summer, and not PhD-only.
3. Updates the catalog. A posting missing from a successful read on two
   different days is closed. A current-season posting the read still returns
   but screening now rejects is removed from the catalog in that run, unless
   it was closed by hand. A company whose read fails is left untouched.
   An empty read counts as a failed read when the company has at least
   `EMPTY_READ_GUARD` open listings, or when its last good read fetched at
   least `EMPTY_FETCH_GUARD` postings ("returned no postings after N last
   time"). Both thresholds are set in
   [`tracker/pipeline.py`](tracker/pipeline.py). That last good fetch count is
   kept in `data/status.json` through failed runs, so the company keeps failing
   until its reader is fixed or its baseline is reset (see Development).
   Companies with no open postings we can read are listed with a link to their
   own internship program page instead.
4. Validates the catalog against
   [`tracker/listing.schema.json`](tracker/listing.schema.json) and regenerates
   this README and `CLOSED.md`.

The run then runs the same checks as CI and, if they pass, commits the day's
data straight to `main` as `data: daily refresh <date>`. It pushes with a
deploy key whose private half is the repository secret `REFRESH_DEPLOY_KEY`.
That key is the one actor allowed to skip review and CI on `main` (see
Development), so the workflow's own checks are what keep bad data off
`main`. It still can't force-push: if `main` moved while the refresh ran, the
push is refused, the run fails, and the next run refreshes from the new `main`.
A real run without the secret fails before reading anything.

Set the repository variable `REFRESH_AUTOMERGE` to `false` to review each
refresh instead: the run pushes a `refresh/<date>` branch and opens a pull
request, and a maintainer approves its CI run, which GitHub holds because a
workflow opened the pull request, then reviews and merges it. A rerun on the
same day force-pushes that branch and reuses the day's pull request if it is
still open, or opens a new one otherwise.

To replace the deploy key, add a new write-access deploy key, store its private
key in `REFRESH_DEPLOY_KEY`, then delete the old deploy key.

Every run, scheduled or dispatched, lists the companies whose read failed
(their `[failed]` lines) in the job summary and adds a warning annotation for
each one, whether or not anything is pushed. A refresh pull request lists the
same failed reads in its body. If every company fails, the run writes
nothing and the job fails. The reporting is done by
[`.github/scripts/failed-reads.sh`](.github/scripts/failed-reads.sh).

The workflow can also be dispatched by hand from the Actions tab (**Daily
refresh** → **Run workflow**):

- With **dry run** ticked, it runs `python -m tracker refresh --dry-run` and
  puts the per-company `[ok]` / `[failed]` lines in the job summary. It writes
  nothing, skips the checks and opens no pull request. Pick a feature branch in
  **Use workflow from** to try that branch's readers and `companies.toml` on
  GitHub's runners before merging.
- Without it, the run is a real refresh, the same as the scheduled one. A real
  refresh only runs on `main`: dispatched on any other branch it fails at its
  first step, before reading anything, so data built from unmerged code never
  reaches `main`.

## Development

Requires Python 3.11 or newer.

```bash
python -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"

ruff check . && ruff format --check .
pytest
python -m tracker validate
python -m tracker refresh --dry-run   # live read, writes nothing
python -m tracker render              # rebuild README.md and CLOSED.md
python -m tracker close <listing-id>  # close a listing by hand
python -m tracker add --issue <N> -   # accept an "Add internship" issue (body on stdin)
python -m tracker reset-baseline "<company>"  # accept that a board is really empty
```

When a company really has emptied its board, its reads keep failing with
"returned no postings after N last time". Run `python -m tracker reset-baseline
"<company>"` and open a pull request with the `data/status.json` change. It
clears that company's last good fetch count, so the next empty read is accepted.

`main` is protected by three repository rulesets:

- **Protect main history:** nobody can force-push or delete `main`.
- **Require CI:** changes need passing CI checks (`test (3.11)` and
  `test (3.13)`). Only the daily refresh's deploy key skips this; the refresh
  runs the same checks itself before pushing.
- **Require review:** changes come through a pull request approved by the
  maintainer. The maintainer's own pull requests don't need approval: merge them
  once CI passes, using GitHub's "bypass rules" merge option
  (`gh pr merge --admin`). The deploy key skips this too.

Tests mock all HTTP and never touch the network. To add a company on a supported
platform, add an entry to `companies.toml`. To add a platform, see
`tracker/sources/__init__.py`. When a company moves to a reader that fetches
nothing (such as `careers_page`), run `python -m tracker reset-baseline
"<company>"` in the same pull request; otherwise its last good fetch count stays
and its first empty read, and every one after it, fails.
